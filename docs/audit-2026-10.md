## A. overnight-a-harden (prefix A-): main health, e2e, security, accessibility

Context to draw on: merge regressions between the two histories, full e2e runs, `pnpm audit`, axe in light and dark, portal `/open/[id]`.

### Keep this

- Forced row level security on 58 tables, with `app.business_id` and `app.user_id` set per transaction by `withTenant` (`packages/db/src/index.ts:40-50`), and a web role that is not BYPASSRLS. The strongest part of the system design.

- Migrations under an advisory lock, tolerant of out of order history, tested from empty.
- An e2e suite on a production build with a real worker and a mock GSP. It found a real bug and a real merge regression in one run. Keep it as the merge gate (with `prepare-db` and reduced motion).
- `access-themes.spec.ts`: one place that fails when a page or colour breaks accessibility in either theme.
- `GET /api/health` reports only up or down; the cron tick refuses every caller unless `CRON_SECRET` has 16 or more characters and compares in constant time (`apps/web/app/api/cron/tick/route.ts:18-22`).

### Failure modes worth rehearsing

1. **A queued WhatsApp send never arrives** (D-1). The customer presses Send twice and two messages go out when the cron finally runs. Fix: the worker, first.
2. **A migration is merged before it is applied.** The deploy succeeds and the first page that reads the new table returns 500. D-7 is the guard.
3. **The Razorpay secret is wrong after the switch to live.** Webhooks return 400, Razorpay retries, invoices stay unpaid although customers paid. Mitigation: the Rs 1 live test and an alert on `webhook_event where processed_at is null`.
4. **The database is lost or corrupted.** With no scheduled backup and no drill, recovery time is unknown (D-6). Everything else here is recoverable; this is not.
5. **The GST partner or portal is down.** Handled well: invoices show not yet registered, retries go 30 s doubling to an hour for 8 tries, then Resubmit (`packages/core/src/jobs.ts:31-34`).

### What must exist before real customers

Worker deployed and a delivery tested within minutes (D-1). One restore drill done (D-6). An uptime check and a daily queue check that reach a human (D-2). Real legal text and prices (D-5). A real SMS sign-in, one real WhatsApp message and a Rs 1 Razorpay payment (D-16). `KORA_ALLOW_MOCKS` and its siblings confirmed unset in production (D-15). `einvoice_enabled` left off until a partner is chosen (D-17). The "who to call" table filled in. The rest can follow in the first weeks.

### Keep this

- **The database enforces the legal rules**: gapless numbering, frozen issued documents, totals equal the sum of lines, one payment per event, append-only audit (`packages/db/migrations/0001_init.sql:296-345`, `document_guard`). An application bug cannot break them.
- **Jobs are written in the same transaction as the change**, claimed with `SKIP LOCKED`, retried with jitter, with a permanent-error path (`packages/core/src/jobs.ts:18-34`). Webhooks are idempotent by event id, and invoice creation takes an `Idempotency-Key` (verified locally: 201 then 200, same number).
- **Fail-closed mocks in production** (`apps/web/lib/server.ts:45`); the cron and admin routes refuse everyone without a 16-character secret and compare in constant time (`apps/web/app/api/cron/tick/route.ts`).
- **RLS with a membership check** (`is_authorized()`), so removing a user ends access at the database. `kora_web` is neither superuser nor `BYPASSRLS` (verified with `pg_roles` on a migrated database).
- **Money is integer paise** everywhere, with 10,000-run property tests (`packages/tax/test/property.test.ts:6`).
- **A safe backup design** (custom-format dump, read-back check, encryption, restore check) that only needs switching on and rehearsing.
- **Drift tests and an honest checklist**: `apps/web/test/apiDocs.test.ts`, `envDocs.test.ts`, `docsLinks.test.ts`, and the launch checklist with Done, Not done and Unknown.

None of the five found a data-loss bug in what exists, and several independently praised the same things (forced RLS on 58 tables, money as bigint paise, jobs written in the same transaction as the change, idempotent webhooks, the e2e suite as a merge gate). They also independently found the same five weaknesses. Those are the plan.

### The five themes (system design first)

1. **Background work does not run.** The only scheduler is one daily Vercel cron; the worker is not deployed (D-1 Critical, A-07, C-12, D-14, D-18). Jobs can run twice if a handler is slow (C-11). Code can fix the plumbing (scheduler workflow, heartbeat, non-root worker image); hosting the worker is the owner's call.
2. **Money correctness rests on conventions the database does not enforce.** Two parallel credit notes both succeed (C-1 High, reproduced), no constraint stops over-crediting (C-6), a gateway payment on a written-off invoice (C-10), GSTIN state codes (C-7, T-9), unbounded amount in words (T-10).
3. **Schema and code can drift, and nothing says so.** Migrations are applied by hand; the hosted database was behind the code twice (A-08, D-7, D-8, D-9, C-20). Health does not report schema version, and one stray env flag turns on mock sign-in in production (D-15, B-6, D-14).
4. **Trust boundaries are wider than they look.** 13 tables have no RLS and `kora_web` can read them (A-05, D-12), four definer functions are executable by PUBLIC (A-06), rate limiting fails open and is partly in-process (A-09, D-13), sign-up enumerates accounts (B-7), no script CSP (A-11, B-16, T-13).
5. **The safety net is slow, noisy and partly blind.** CI runs everything twice and serially (A-03, A-04, T-3), the e2e database is not reset (A-12), main was red for unrelated reasons (T-2), there is no alerting or queue-age check (D-2, D-3), no bundle budget (T-4), and the camera policy silently breaks a shipped tool (B-1, T-1 High).
